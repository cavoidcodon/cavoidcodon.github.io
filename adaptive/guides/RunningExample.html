    About This Guide#

    All guides of the series show their topic on one invented system: the high-performance ECU HPC, which runs a camera- and radar-based ADAS feature. This guide is the master definition of that system. It describes the vehicle around HPC, the machine itself, its Function Groups, processes and services, its network deployment, its persistent data, diagnostics, updates, security and safety, and it names for each element the guide that explains it in detail. It does not explain a functional cluster. The main page introduces the series, and the Series Glossary defines the terms used here.

    Who This Guide Is For#

    Everyone who reads the series, in particular:

    • Application developers who write software that runs on the Adaptive Platform.
    • Integrators who configure manifests, deploy software and debug ECUs.
    • Platform developers who build or extend functional clusters.

    Assumed background: modern C++, plus basic Linux/POSIX knowledge. No prior AUTOSAR knowledge is needed.

    What You Will Get From This Guide#

    After reading this guide you will be able to:

    1. Describe the HPC running example: its network, Function Groups, processes and services.
    2. Find the guide that explains a given part of the example in detail.
    3. Find the scenario on the running example that each guide tells.

    1. The HPC Reference System#

    Why this matters: Abstract concepts are easier to learn on a concrete system. All guides use the same invented ECU, so that what you learn in one guide connects to the next. This chapter is the master definition of that system. It stays skeletal on purpose: each element names the guide that explains it in detail.

    1.1 Purpose and Rules#

    HPC is a fictional high-performance ECU that runs a camera- and radar-based ADAS feature. It is small enough to keep in your head, but it touches every functional cluster of the series. It is not a real product. The Function Groups, the processes, their states and their Execution Dependencies were introduced by the EM guide.

    Guide Manifests writes a part of the example as real ARXML (Section 12.16). All its model elements live in the top-level package /HPC, in sub-packages named after the recommended package of each element kind, for example /HPC/ServiceInterfaces, /HPC/Executables and /HPC/Processes. Standardized data types, such as uint8_t, are taken from the package /AUTOSAR/StdTypes that AUTOSAR publishes. The Manifests guide owns this package structure.

    Note: HPC is also the general AUTOSAR abbreviation for a high performance computer. In the series, HPC in code font always means the machine of the running example.

    1.2 The Vehicle Context#

    The ADAS feature on HPC works like this. A front camera, attached to HPC, and the smart radar sensor FrontRadar observe the road. HPC combines their data with the vehicle speed, steering angle and yaw rate from the chassis, and computes a list of detected objects. The Cockpit computer shows the camera image and the objects to the driver, and the InstrumentCluster shows whether the ADAS feature is active. Software updates arrive over the air through the TelematicsUnit, and workshops connect a DiagnosticTester.

    The following diagram shows the network topology.

    Node Platform Role in the example IPv4 (illustrative) Owner guides
    HPC Adaptive Platform; the only node that is detailed Runs the ADAS feature 192.168.10.10 all
    CentralGateway Classic Platform, black box Ethernet switch; routes PDUs between the CAN bus and HPC; time master; sends PowerMode; access point for the DiagnosticTester 192.168.10.1 Network Bindings, NM/TSync/RDS, Diagnostics Part 1
    ChassisECU Classic Platform, CAN Sends VehicleSpeed, SteeringAngle and YawRate (CAN only) Network Bindings
    InstrumentCluster Classic Platform, CAN Shows AdasStatus to the driver (CAN only) Network Bindings
    FrontRadar Smart sensor, not AUTOSAR Streams raw radar detections to HPC 192.168.10.30 NM/TSync/RDS
    Cockpit Black box; its platform is not specified Shows the camera image, the detected objects and the ADAS status 192.168.10.20 CM, Network Bindings, IDSM and Firewall
    TelematicsUnit Adaptive Platform, black box Hosts the OTA Client and Vehicle Update and Configuration Management (V-UCM); connects the vehicle to the Backend 192.168.10.40 UCM
    DiagnosticTester Off-board Sends UDS requests over DoIP (assigned when connected) Diagnostics Part 1, Diagnostics Part 2
    Backend Off-board Provides update packages; receives qualified security events (off-board) UCM, IDSM and Firewall

    Note (simplification): A real ADAS ECU also controls actuators, such as brakes and steering, and uses more sensors. The example leaves them out. Its final output is the object list.

    Software Clusters. A Software Cluster is the unit in which software is deployed and updated. Each Machine has exactly one Software Cluster with the category PLATFORM_CORE. It is expected to contain at least Execution Management, State Management and Update and Configuration Management, because these are needed to install any further software. A Function Group belongs to exactly one Software Cluster (SW Architecture, Sections 12.2 and 13.4). HPC has two Software Clusters:

    Software Cluster Category Version Function Group Contents Owner guides
    HpcPlatformCore PLATFORM_CORE 1.0.0 MachineFG The operating system, Execution Management, the processes StateManager, SmControl, PlatformHealth and PowerControl, the daemons of the other platform clusters, and the platform libraries Manifests, UCM
    AdasCluster APPLICATION_LAYER 1.0.0, later 1.1.0 (Section 1.11) ADAS The seven ADAS processes and their configuration Manifests, UCM

    Each Software Cluster carries the ID of its vendor and is signed by that vendor: HpcPlatformCore has the vendor ID 0x1111 and is signed with PlatformVendorCert; AdasCluster has the vendor ID 0x1234 and is signed with AdasSupplierCert (Section 1.12). The Manifests guide shows both Software Clusters as ARXML.

    Platform daemons. Besides StateManager and PlatformHealth, HpcPlatformCore contains the daemons of Communication Management, Diagnostic Management, Update and Configuration Management, Cryptography, the Intrusion Detection System Manager, the Firewall, Network Management and Time Synchronization. EM starts them in MachineFG.Startup. Their process names are vendor-specific, so the series calls them by their cluster, for example "the UCM daemon". Library-based clusters, such as Log and Trace, Persistency, Core and Raw Data Stream, run inside the processes that use them.

    1.4 Function Groups and States#

    HPC has two Function Groups, both defined in the EM guide:

    • MachineFG controls the machine lifecycle. States: Off, Startup, Driving, Shutdown, Restart and Verify. Driving is project-specific; the others are mandatory.
    • ADAS controls the ADAS feature. States: Off, Normal, Degraded and Verify. The Manifest Specification requires a Verify state in every Function Group ([constr_10023]). State Management switches ADAS to Verify while an update of AdasCluster is activated; the UCM guide decides which processes run in it.

    The following diagrams show the main transitions. EM performs every transition; it initiates only Off → Startup of MachineFG itself. All other transitions are requested by State Management.

    Transition Requested by State Management when ... Owner guides
    MachineFG: Off → Startup (not SM: EM performs it on its own at boot) EM
    MachineFG: Startup → Driving startup is complete and PowerMode reports that the vehicle is switched on SM
    ADAS: Off → Normal the machine is in Driving. SM also requests the partial network AdasPn. SM, NM/TSync/RDS
    ADAS: Normal → Degraded PHM reports a supervision failure of Fusion or CameraDriver, EM reports that Fusion crashed (ExecutionError 42), or a diagnostic request asks for it through SmControl EM, SM, PHM, Diagnostics Part 1
    ADAS: Degraded → Normal not during a drive. ADAS returns to Normal only when it is started again, at the next drive cycle through Off; this also restarts a failed CameraDriver SM
    ADAS → Off, then MachineFG → Shutdown PowerMode reports that the vehicle is switched off EM, SM
    MachineFG → Restart Diagnostic Management requests an ECU reset through SmControl, or UCM requests a machine reset SM, Diagnostics Part 1, UCM
    ADAS: Off → Verify → Normal UCM activates an update of AdasCluster: SM switches ADAS off, then to Verify to check the new software, and finally back to Normal (Platform Design, Figure 13.10) SM, UCM
    MachineFG → Verify UCM activates an update that affects MachineFG, that is, the HpcPlatformCore Software Cluster SM, UCM

    State Management design. HPC uses the StateMachine approach of State Management (the SM guide, Section 1.4). The process StateManager runs two StateMachines; the project-specific application SmControl decides which transitions to request (the SM guide, Section 7.6). All values are illustrative.

    StateMachine Role Controls StateMachine States (initial in bold) Transition requests (value) Error reactions
    HpcController Controller MachineFG; starts and stops AdasAgent Init, Driving, Shutdown, Restart, PrepareUpdate, VerifyUpdate, PrepareRollback, AfterUpdate, ContinueUpdate, LeaveSuspend Drive (1), PowerOff (2), Reset (3) ANY → Restart
    AdasAgent Agent ADAS and the partial network AdasPn (network handle AdasPnHandle) Off, Normal, Degraded, PrepareUpdate, VerifyUpdate, PrepareRollback Degrade (10), from Normal only 42 → Degraded; 1 → Degraded; ANY → Off

    The Off state of AdasAgent keeps AdasPn for an afterrun of 2 s before it releases it. HPC does not use Suspend-to-RAM; LeaveSuspend exists only because R25-11 requires it in every Controller (the SM guide, Section 10.8). The SM guide, Section 12.12 gives the complete configuration.

    The Execution Dependencies are unchanged from the EM guide: CalibrationCheck needs Storage Running; LoggerCompanion needs LegacyLogger Running; Fusion needs CalibrationCheck Terminated and LoggerCompanion Running; FusionLite needs LoggerCompanion Running.

    Software components and instance specifiers. The Manifests guide (Section 5.5) models the executables camera_driver and fusion with one software component each, CameraDriverSwc and FusionSwc, placed in the root prototype Root of the executable. Their ports for CameraService are CameraPPort (provided) and CameraRPort (required). The application code therefore identifies them with the instance specifiers /camera_driver/Root/CameraPPort and /fusion/Root/CameraRPort. For Platform Health Management, FusionSwc also has the R-port FusionCyclePort and CameraDriverSwc the R-port ImageLoopPort, typed by the Supervised Entity interfaces FusionCycle and CameraImageLoop (Section 1.13); their instance specifiers are /fusion/Root/FusionCyclePort and /camera_driver/Root/ImageLoopPort. Other executables are modeled in the same way when a guide needs them. The CM guide adds the ports of ObjectListService and CalibrationDataService: FusionSwc has the P-port ObjectListPPort and the R-port CalibrationRPort, and CameraDriverSwc the R-port CalibrationRPort. The executables fusion_lite, storage and calib_check hold the components FusionLiteSwc (ObjectListPPort, CalibrationRPort), StorageSwc (CalibrationPPort, ObjectListRPort) and CalibrationCheckSwc (CalibrationRPort) in their root prototypes Root, so that the code uses specifiers such as /fusion/Root/ObjectListPPort, /storage/Root/CalibrationPPort and /calib_check/Root/CalibrationRPort. The FieldSenderComSpec of ObjectListPPort gives the field FusionMode the initial value Full in FusionSwc and RadarOnly in FusionLiteSwc (the CM guide, Section 14.11).

    State Management ports and process states. The executable state_manager has, in its root prototype Root, the R-ports MachineFgPort and AdasFgPort, typed by the State Client interfaces MachineFgStateClient and AdasStateClient, so that the code uses the instance specifiers /state_manager/Root/MachineFgPort and /state_manager/Root/AdasFgPort. The Function Group Port Mappings StateManagerToMachineFG and StateManagerToADAS connect the two ports of the process StateManager to MachineFG and ADAS (EM guide, Section 13.10). The root prototype is typed by the component StateManagerSwc. For Platform Health Management, it also has the P-port PhmRecoveryPort, typed by the recovery notification interface SupervisionRecovery, and the R-port HeartbeatPort, typed by the Supervised Entity interface StateManagerHeartbeat (Section 1.13); the instance specifiers are /state_manager/Root/PhmRecoveryPort and /state_manager/Root/HeartbeatPort. For its StateMachines, StateManagerSwc has P-ports for the services of each StateMachine (ControllerServicePort, AdasServicePort, ControllerStatePort, AdasStatePort), for UpdateAllowedService (UpdateAllowedPort) and for UpdateRequest (UpdateRequestPort), and R-ports as inputs of its tables (ControllerTriggerPort, AdasTriggerPort, ControllerErrorPort, AdasErrorPort). SmControl is modeled by the component SmControlSwc in the root prototype Root of sm_control, with the ports PowerModeRPort, VehicleDynamicsRPort, AdasStatusPPort, ControllerRequestRPort, AdasRequestRPort, AdasStateRPort, UpdateAllowedRPort and EcuResetPort (the SM guide, Section 12.9). The processes that others depend on (Storage, CalibrationCheck, LegacyLogger, LoggerCompanion) have a process state machine typed by the group ProcessStates, with the states Running and Terminated (EM guide, Section 13.11).

    Pitfall: Service use is not an Execution Dependency. Fusion uses CameraService, but it has no Execution Dependency on CameraDriver. It waits for the service through Service Discovery, as the EM guide recommends (EM guide, Section 6.6).

    The CameraService contract (detailed in the Manifests guide, Section 6.6). Namespace hpc::camera, version 1.0. The event Image carries a CameraImage: timestamp (uint64_t), width and height (uint16_t) and pixels (a vector of uint8_t). The field CameraStatus has the type CameraState with the values Ok, Blocked and NotAvailable; it has a getter and a notifier but no setter, and its initial value is NotAvailable. The method SetExposureMode(mode) takes an ExposureMode with the values Auto, Day and Night, and can fail with the application error ExposureModeNotSupported (code 1 of the error domain CameraErrors). Fusion calls SetExposureMode(Night) when the camera image gets dark; if CameraDriver answers ExposureModeNotSupported, Fusion keeps the mode Auto (the Core guide, Section 9.7).

    The ObjectListService contract (detailed in the CM guide, Section 14.11). Namespace hpc::fusion, version 1.0. The event ObjectList carries an ObjectListData: timestamp (uint64_t, VehicleTime) and objects, a vector of DetectedObject with id (uint16_t), kind (ObjectKind with the values Unknown, Vehicle, Pedestrian and Cyclist), x and y (float, in metres) and vx and vy (float, in metres per second). The field FusionMode has the type FusionModeType with the values Full and RadarOnly; it has a getter and a notifier but no setter. Fusion publishes Full, FusionLite publishes RadarOnly.

    The CalibrationDataService contract (detailed in the CM guide, Section 13.5). Namespace hpc::storage, version 1.0. The method GetCalibration(key) returns the CalibrationRecord of a CalibrationKey (CameraExtrinsics or RadarAlignment, the keys of CalibrationKvs) or fails with CalibrationNotFound; SetCalibration(key, record) stores a record or fails with CalibrationRejected. A CalibrationRecord has values (a vector of float) and writtenAt (uint64_t). After each successful SetCalibration, Storage sends the trigger CalibrationUpdated, and Fusion and FusionLite read the calibration again. The skeletons of CameraDriver and Storage execute method calls with the processing mode kEventSingleThread.

    Error domains. Every error belongs to an error domain, and the identifier of each domain must be unique in the platform. Application domains use identifiers whose most significant bit is 0 (the Core guide, Section 7.4). The example has four domains:

    Error domain Identifier Namespace Errors (code) How it is defined Owner guides
    CameraErrors 0x1001 (4097) hpc::camera ExposureModeNotSupported (1) Modeled; referenced by SetExposureMode, so its C++ code is generated Manifests, Core, CM
    AdasExecutionErrors 0x1002 (4098) none FusionFailed (42), AdasStateTimeout (60), AdasTransitionRequestFailed (61) Modeled; 42 is the processExecutionError of Fusion; 60 and 61 are error codes of the State Management configuration Manifests, EM, SM
    FusionErrors 0x1003 (4099) hpc::fusion kInputTimeout (1), kCalibrationImplausible (2) Written by hand inside Fusion, not modeled; used only inside the process Core
    CalibrationErrors 0x1004 (4100) hpc::storage CalibrationNotFound (1), CalibrationRejected (2) Modeled; referenced by GetCalibration and SetCalibration of CalibrationDataService CM, Persistency

    Three design decisions are worth knowing:

    • Shared data goes through a service. Persistent data is private to one process (Platform Design, Section 10.1). CalibrationCheck and Fusion therefore cannot read data that another process stored. Storage owns the calibration and shares it through CalibrationDataService.
    • Two providers, never at the same time. Fusion and FusionLite both provide ObjectListService, but they run in different ADAS states. They offer the same service instance, so the proxy of Storage simply reconnects after a switch (the CM guide, Section 9.6); the Network Bindings guide shows the DDS deployment.
    • The ADAS status comes from SmControl, which follows the CurrentState of the StateMachine AdasAgent in State Management.

    Standardized platform services, such as the PackageManagement service of UCM or the services of State Management (StateMachineService and StateMachineNotification for each StateMachine, UpdateAllowedService and UpdateRequest), are used as the specifications define them. The running example does not redefine them.

    1.8 Classic ECUs and Signal-to-Service Translation#

    The Classic ECUs on the CAN bus exchange signals, not services. Signal-to-Service translation in Communication Management maps these signals to service elements on HPC, and back. The following diagram shows the path of the vehicle dynamics signals and of the ADAS status.

    Signals Sender → receiver PDU (CAN ID, cycle; illustrative) Service on HPC
    VehicleSpeed, SteeringAngle, YawRate ChassisECU → HPC ChassisDynamics (0x101, 10 ms) VehicleDynamicsService
    PowerMode CentralGateway → HPC VehicleMode (0x120, 100 ms) PowerModeService
    AdasStatus HPC → InstrumentCluster AdasHmi (0x2A0, 100 ms) AdasStatusService

    The Adaptive Platform communicates over Ethernet at the data link layer (Platform Design, Section 8.1). HPC therefore has no CAN interface of its own: CentralGateway routes the PDUs between the CAN bus and HPC. The Network Bindings guide explains how Communication Management receives these PDUs and maps them to services.

    The signals have this layout (illustrative; all signals little endian, as is common on CAN):

    PDU Signal Start bit, length Type and scaling
    ChassisDynamics (8 bytes) VehicleSpeed 0, 16 bit unsigned, 0.01 km/h per bit
    SteeringAngle 16, 16 bit signed, 0.1 degree per bit
    YawRate 32, 16 bit signed, 0.01 degree/s per bit
    ChassisDynamicsCrc 48, 8 bit E2E CRC (PROFILE_11)
    ChassisDynamicsCounter 56, 4 bit E2E counter
    ChassisDynamicsDataIdNibble 60, 4 bit High nibble of the E2E data ID 0x101
    VehicleMode (1 byte) PowerMode 0, 2 bit 0 = Off, 1 = On
    AdasHmi (1 byte) AdasStatus 0, 3 bit 0 = Off, 1 = Active, 2 = Degraded, 3 = Unavailable

    Protection (the Secure Communication guide). VehicleSpeed, SteeringAngle, YawRate and the three E2E header signals form the signal group ChassisDynamicsGroup, protected end-to-end by ChassisECU with PROFILE_11 (data ID 0x101, lower12Bit); the translation on HPC is a safe translation. CentralGateway sends VehicleMode as the secured PDU VehicleModeSecured (5 bytes: the 1-byte PDU, an 8-bit truncated freshness value and a 24-bit truncated MAC; SecOC Profile 1, SecOC data ID 0x0120, freshness value ID 1, key VehicleModeSecOcKey); the translation of PowerMode is a secure translation. AdasHmi is not protected.

    On the Ethernet side, the PDUs use the Signal-Based SOME/IP binding with the Partial SOME/IP Header: each PDU is preceded by a 4-byte Message ID (service ID and event ID plus 0x8000) and a 4-byte length. CentralGateway offers the translated services with SOME/IP service discovery and subscribes to the one that HPC provides.

    1.9 Persistent Data#

    Storage Kind Owner process Content Notes Owner guides
    CalibrationKvs Key-Value Storage Storage Key CameraExtrinsics (mounting angles and position of the camera) and key RadarAlignment (angular offset of the radar) Protected by a message authentication code (MAC) with CalibrationMacKey. Changed only through SetCalibration. Persistency, Cryptography
    Recordings File Storage Storage Recorded object lists, one file per recording Limited by a quota; the oldest recording is deleted first Persistency
    FusionParams Key-Value Storage Fusion Key TrackerTuning: tuning parameters that Fusion learns while driving Migrated by the update to AdasCluster 1.1.0, which changes the data type of TrackerTuning Persistency, UCM

    Ports and interfaces. Each storage is reached through an R-port of the software component of its process: CalibrationKvsPort and RecordingsPort in StorageSwc (instance specifiers /storage/Root/CalibrationKvsPort and /storage/Root/RecordingsPort), and FusionParamsPort in FusionSwc (/fusion/Root/FusionParamsPort). The ports are typed by the persistency interfaces CalibrationKvsInterface, RecordingsInterface and FusionParamsInterface, all with the access mode readWrite. The values of CalibrationKvs have the type CalibrationRecord of CalibrationDataService; their initial values CameraExtrinsicsDefault and RadarAlignmentDefault mean "not calibrated" (an empty value list).

    TrackerTuning in two versions. fusion 1.0.0 stores hpc::fusion::TrackerTuningV1 (gateDistance as float in metres, maxCoastCycles as std::uint8_t). fusion 1.1.0 uses hpc::fusion::TrackerTuningV2 (gateDistance, maxCoastCycles as std::uint16_t, and the new minConfidence as float), raises the contract version of FusionParamsInterface from 1.0.0 to 1.1.0, and declares the old type as the previous data type. When Fusion 1.1.0 opens FusionParams for the first time after the update, its update callback reports the old contract version; Fusion then converts the stored value and removes the backup (the Persistency guide, Section 12.12).

    Target configuration (illustrative values; the Persistency guide, Section 14.13 has the details):

    Storage Version Update strategy Minimum / maximum size Integrity and security
    CalibrationKvs 1.0.0 keep existing 16 KiB / 64 KiB 2 out of 3 copies for the whole storage, in two locations; MAC MAC/CMAC/AES-128 with the key slot CalibrationMacKeySlot, which holds CalibrationMacKey
    Recordings 1.0.0 keep existing 64 MiB / 256 MiB, at most 64 files none: recordings can be made again
    FusionParams 1.0.0, 1.1.0 in AdasCluster 1.1.0 keep existing 4 KiB / 16 KiB CRC CRC_32P4 (32 bits) per key-value pair

    Storage syncs CalibrationKvs after every accepted SetCalibration and answers CalibrationNotFound when a key cannot be read or authenticated. It syncs a recording every 10 s and when the recording ends, and it deletes the oldest recording when the quota or the file limit is reached.

    1.13 Safety#

    Platform Health Management supervises three processes. Each one reports the checkpoints of one Supervised Entity, and its supervisions form one Global Supervision. All values are illustrative.

    Supervised process Supervised Entity: interface, namespace, checkpoints (ID) Supervisions Global Supervision, active in Owner guides
    Fusion FusionCycle, hpc::fusion: CycleStart (1), InputsRead (2), ObjectsPublished (3), CycleEnd (4) Alive supervision of CycleStart: reference cycle 200 ms, 4 expected indications, margins 1 and 1, tolerance 1 failed cycle. Deadline ComputeDeadline: InputsRead to ObjectsPublished within 25 ms. Deadline CycleDeadline: CycleStart to CycleEnd within 45 ms. Logical supervision CycleOrder: CycleStart, InputsRead, ObjectsPublished, CycleEnd, or CycleStart directly to CycleEnd when a cycle is skipped. FusionSupervision, in ADAS.Normal PHM
    CameraDriver CameraImageLoop, hpc::camera: ImageCaptured (1) Alive supervision of the image loop (30 images per second): reference cycle 500 ms, 15 expected indications, margins 2 and 2, tolerance 2 failed cycles CameraDriverSupervision, in ADAS.Normal and ADAS.Degraded PHM
    StateManager StateManagerHeartbeat, hpc::sm: MainLoop (1) Alive supervision of the main loop (every 100 ms): reference cycle 1 s, 10 expected indications, margins 2 and 2, tolerance 1 failed cycle; expiredSupervisionTolerance 200 ms StateManagerSupervision, in every MachineFG state except Off PHM

    The configuration is split into two PHM contributions. AdasPhm belongs to AdasCluster. It holds the supervisions of Fusion and CameraDriver, and it connects both Global Supervisions to the recovery notification AdasRecovery (timeout 6 s). The mapping AdasRecoveryToStateManager delivers that notification to the port PhmRecoveryPort of StateManager. PlatformPhm belongs to HpcPlatformCore and holds the supervision of StateManager. It has no recovery notification, because a failure of State Management ends in a watchdog reset. The mappings AdasPhmToHpc and PlatformPhmToHpc enable both contributions on HPC. In a real project, the platform vendor usually delivers the supervision of State Management.

    When a supervision of Fusion or CameraDriver fails, Platform Health Management informs State Management, which switches ADAS to Degraded through the error reactions of AdasAgent. PHM passes the processExecutionError of the failed process: 42 for Fusion, and the default value 1 for CameraDriver, which has none. When Fusion terminates, EM informs PHM, because Fusion is supervised (EM guide, Section 5.9). PlatformHealth also serves the hardware watchdog: if Execution Management or State Management fails, PHM lets the watchdog reset the machine (Platform Design, Section 17.3). End-to-end (E2E) protection (the Secure Communication guide) covers the signal group ChassisDynamicsGroup (PROFILE_11, safe translation for Fusion, FusionLite and SmControl), the method SetExposureMode of CameraService (PROFILE_04m) and the notifier of AdasStatus to Cockpit (PROFILE_04). ObjectListService uses DDS, where liveliness and deadline QoS take the role of E2E.

    Key takeaways

    • HPC is the only detailed node. The other nodes are black boxes that give the example realistic network traffic.
    • HPC has two Software Clusters: HpcPlatformCore with MachineFG, and AdasCluster with ADAS.
    • The ten processes of the EM guide stay unchanged; the SM guide adds SmControl. Their roles now include services, storages, diagnostic functions and supervision.
    • Every element names its owner guide. Illustrative values are invented for teaching.
    • New elements are always added to this guide first.
